# **HotStuff Protocol Analysis — Four Executions**

This analysis uses the four original uploaded log files. It examines event frequencies, replica participation, vote ordering, view-level differences, and causal relationships between protocol events.

## **1. Experimental setup**

All four executions use the same logged configuration:

| Parameter          | Configuration          |
| ------------------ | ---------------------- |
| Protocol           | Chained HotStuff       |
| Replicas           | 4 (hs1–hs4)            |
| Leader rotation    | Round-robin            |
| Cryptography       | ECDSA                  |
| Communication      | Clique                 |
| View timeout       | 500 ms                 |
| Clients            | 1                      |
| Log level          | Debug                  |
| Byzantine strategy | No strategy configured |

The runs differ substantially in how many views they complete.

**Initial finding:** Runs 1 and 4 have very similar progression, Run 3 reaches fewer views, and Run 2 reaches substantially fewer views than all the others.

This difference alone does not establish replica misbehaviour or a protocol failure. It is important to examine whether each execution advances normally through its views and whether timeout or certificate-related events coincide with reduced progression.

Importantly, Run 2 also contains proposals that reference parent QCs from nonconsecutive views. This provides a more specific reason to investigate its behaviour than simply observing that its event totals are smaller.

| Proposal view | Proposer | Vote collector | Recorded vote order |
| ------------- | -------- | -------------- | ------------------- |

This suggests the logging and vote-processing mechanism has a recurring collection-order structure. It does not establish network latency rankings, because log order is not a direct measurement of message transmission time.

## **4. Comparing protocol events by view**

### **4.1 Views shared by all four executions**

All four logs contain proposal views **1 through 1,119**, plus genesis view 0.

This gives 1,119 directly comparable proposal views. Beyond view 1,119, Run 2 cannot be included in four-way comparisons.

For view matching, I used two keys:

1. View number alone: `(view)`.
2. View number together with proposer: `(view, proposer)`.

### **4.2 Does proposer identity change the comparison?**

In the 1,120 shared block views including genesis, proposer identity matches in all four runs.

| Matching method  | Common block views | Views with complete vote sequences across all runs | Views sharing at least one identical complete vote order |
| ---------------- | ------------------ | -------------------------------------------------- | -------------------------------------------------------- |
| View number only | 1,120              | 1,106                                              | 132                                                      |
| View + proposer  | 1,120              | 1,106                                              | 132                                                      |

**Finding:** Including proposer identity does not change the matched results in this dataset.

This follows the observed round-robin leader assignments. Proposer identity is still worth recording in the analysis, particularly when studying executions with different leader-selection configurations or faulty-leader scenarios.

### **4.3 Views with similar and different behaviour**

At views 1 and 2, the four runs exhibit the same general progression pattern: proposal reception, vote collection, new-view dispatch and subsequent view advancement.

At view 3, all four executions contain timeout activity. They nonetheless form complete vote sequences, so the presence of a timeout message is not by itself evidence that consensus stopped.

A more substantial difference appears in **Run 2, particularly around views 896–914**.

This distinction matters: timeouts occur repeatedly, but most are associated with different view numbers between executions.

## **5. Relationships and ordering between protocol events**

The most important part of the analysis is determining whether the events form a logically connected progression rather than simply occurring frequently.

### **5.1 Expected progression**

**Proposal Bᵥ**

Contains parent QC and parent block hash

**Receive proposal and process parent QC**

Potential HighQC update and view advancement

**Validate proposal and vote**

Next leader collects and verifies distinct votes

**QCᵥ and OnNewView**

Update HighQC and advance toward view v+1

**Next proposal Bᵥ₊₁**

Extends a certified block; chained certification supports commit and execution

Alternative path: timeout certificates can support view changes when normal QC-driven progression is delayed.

### **5.2 Verified example: Run 2, views 1–3**

The beginning of Run 2 provides a concrete sequence.

**View 1 — block&#x20;**`fn6yGE0b`

Log evidence

Line 91: `CollectVote: dispatching event for new view (current : 1)`.

Line 92: `OnNewView (from network: false)`.

Line 93: hs3 processes QC for `fn6yGE0b`, view 1.

**View 2 — block&#x20;**`Sxxt8pzb`

Line 97: hs3 processes a block referencing `fn6yGE0b` as both parent hash and attached QC hash.

Lines 100–102: other replicas receive the view-2 proposal and begin processing the attached QC.

Lines 122–125: hs4 collects votes from replicas 4, 3, 1 and 2 for `Sxxt8pzb`.

Lines 126–130: hs4 dispatches a new-view event, processes the QC for view 2, updates HighQC and advances to view 3.

**View 3 — chained commit progression**

Lines 133–136: the commit logic records PRE_COMMIT for the view-2 block, COMMIT for the view-1 block and DECIDE for the genesis block.

This example demonstrates a connected chain:

`fn6yGE0b` → `Sxxt8pzb` → `4xLHdmgy`

The log evidence supports the expected relationship between parent certificates, vote collection, QC-driven advancement and chained commit progression.

It does not directly expose every internal proposal-validation or vote-signature-verification operation, so those steps cannot all be independently confirmed from the logging.

### **5.4 HighQC updates and view advancement**

The logs show two distinct cases.

**Successful update:** `advanceView: Successfully updated HighQC` followed, where appropriate, by `advanceView: Advanced to view N`.

**No update:** `advanceView: HighQC not updated, current view: X, new view: Y`.

A HighQC-not-updated event is not necessarily abnormal. For example, a replica that has already processed a newer QC may receive another copy of an older certificate. Reprocessing it should not lower its HighQC.

This helps explain why there are thousands of HighQC-not-updated messages in all four runs despite continued consensus progress.

The key distinction is whether the replica subsequently advances and continues participating, rather than the number of unsuccessful update attempts alone.

### **5.5 Commit, DECIDE and execution**

All four runs contain sustained PRE_COMMIT, COMMIT, DECIDE and EXEC activity.

Run 2 contains 4,408 DECIDE records and 4,432 EXEC records, so a lower total number of views does not mean consensus completely failed.

Nevertheless, some Run 2 views with incomplete vote collection do not contain normal corresponding QC-dispatch or execution activity.

The aggregate results support the following interpretation:

- Runs 1 and 4 demonstrate sustained chained consensus progression.
- Run 3 demonstrates similarly structured progression over a shorter execution.
- Run 2 demonstrates periods of normal progression interrupted by concentrated timeout and synchronization activity, particularly around views 896–914.

An especially important limitation is that `CollectVote` indicates receipt, not successful signature validation. A complete four-sender sequence therefore establishes complete *logged reception*, not independently verified validity of all four votes.

## **7. Overall conclusions**

The evidence supports five main conclusions.

**First, the executions differ strongly in their total consensus progression.** Runs 1 and 4 reach approximately 3,600 proposal views, Run 3 reaches 2,300, and Run 2 reaches only 1,119. These differences are accompanied by correspondingly different numbers of commit and execution events.

**Second, replica participation is generally balanced.** Proposal reception and vote collection are distributed almost equally across the four replicas within each execution. There is no clear evidence from these aggregate counts that one replica is consistently inactive.

**Third, vote ordering is not entirely random.** The next leader, acting as vote collector, appears first in 98.86% of complete logged vote sequences. However, the identity of that collector rotates, and the ordering of the other replicas varies. No individual replica is consistently first or last across the executions.

**Fourth, comparing views with proposer identity produces the same result as comparing view numbers alone.** The shared proposed views have matching proposers across all four executions. Only 132 of the 1,106 comparable views with complete sequences share an identical complete vote order across all four runs.

**Fifth, Run 2 contains a distinctive disruption around views 896–914.** This interval includes repeated timeout processing, incomplete vote sequences and proposals extending QCs from earlier, nonconsecutive views. The observations suggest temporary disruption to normal QC-driven progression, followed by recovery in subsequent views. They do not, without additional evidence, establish Byzantine behaviour or an implementation error.

### **Important methodological limitations**

The analysis is based on debug logs, not a complete internal execution trace. It therefore cannot prove every successful vote verification, every attempted proposal or every internal state transition.

Global line order also should not be treated as exact causality between different replicas. The strongest event-order evidence comes from messages attributable to the same replica and the same block hash.

The strongest overall finding for a master thesis is that **the four runs preserve broadly similar replica-participation and vote-collection structures, while differing substantially in progress and timeout-related behaviour. Run 2 shows a particularly informative example of how interrupted QC progression, older parent certificates and repeated timeout processing can occur together without permanently preventing subsequent consensus progress.**
